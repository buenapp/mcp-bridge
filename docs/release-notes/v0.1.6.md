## MCP Bridge
v0.1.6

Bug-fix release. Windows `stdio+ssh://` forward mode now completes and exits, regular-file and `/dev/null` stdio work on Linux, and a stdin redirected from a file works on Windows. Adds PuTTY's `plink` as an opt-in ssh client.

### Fixes

- **Windows `stdio+ssh://` forward mode delivered the reply, then never exited** (#23, #26). Four causes, all in the Windows relay:
  - the ssh child's stdin was `std.process.Child`'s synchronous anonymous pipe, which Win32-OpenSSH never reads — it is now an overlapped named pipe;
  - the writer relay's auto-reset event merged "data queued" and "quit" into one wake, so the child's stdin was never closed — the writer now drains to empty, flushes, then closes;
  - the stdin and stdout relay threads looked up their std handles themselves, racing the spawn's handle swap — both are now resolved on the loop thread;
  - the stdout reader did a blocking `ReadFile` with no `OVERLAPPED` on an overlapped pipe — it now does real overlapped reads.
- **Windows: a stdin redirected from a file or `NUL` was never read**, so the bridge hung at 0 bytes. Any non-console stdin is now read; a console is still left alone so interactive OAuth runs keep the keyboard.
- **Linux: a regular-file stdin or stdout hung the bridge** — the known issue listed in v0.1.5. Fixed in born v0.2.1 ([pacyworld/born#4](https://pacyworld.dev/pacyworld/born/issues/4)).
- **Linux: `< /dev/null` failed with `RegisterFailed`**, which is what a service manager hands a process. Fixed in born v0.2.2, which also removes a panic on zero-length socket writes.
- born v0.2.3 makes a refused connect report consistently on Linux ([pacyworld/born#8](https://pacyworld.dev/pacyworld/born/issues/8)).

### New

- **`--ssh-client openssh|plink`** (default `openssh`), with **`--ssh-identity PATH`** (`-i`, both clients) and **`--ssh-hostkey FP`** (plink only). plink is opt-in because it ignores `~/.ssh/config`, accepts only PuTTY `.ppk` keys, and in batch mode refuses a host key it has not cached; `--ssh-hostkey` covers that last case. See the README.

### Project

- The release workflow reads notes from `docs/release-notes/<tag>.md` and reuses an existing release instead of deleting and recreating it, so re-running a tag no longer wipes the notes or duplicates assets.

### Known limitation

- On Windows, `ssh.exe` stops relaying once its stdout is a pipe when it runs **inside a Win32-OpenSSH server session** ([PowerShell/Win32-OpenSSH#1330](https://github.com/PowerShell/Win32-OpenSSH/issues/1330)). The bridge hands it a pipe, so `stdio+ssh://` is not supported when the bridge itself is launched over an ssh login into Windows. Desktop and IDE use are unaffected.

### Verification

- Windows 11, interactive desktop session, spawned the way an IDE does (pipe stdin, pipe stdout, no console window): full `initialize` + `tools/list` against `vnc-mcp-server` returns 22,889 bytes and exits 0 through OpenSSH and through plink; `/bin/date`, a 20,500-byte bulk read, and stdin as pipe, file and `NUL` all exit 0.
- Linux (epoll) client → FreeBSD host: regular-file stdin and stdout, and `< /dev/null`, carry the full 22,889-byte handshake.
- 86/86 tests pass; clean builds for `x86_64-freebsd`, `x86_64-linux-gnu`, `x86_64-windows-gnu`.
