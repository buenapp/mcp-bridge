## MCP Bridge
v0.1.5

Bug-fix release. `stdio+ssh://` and `stdio+tcp://` forward mode were unusable; this makes them work.

### Fixes

- **Forward mode relayed nothing and hung on stdin EOF** (#18, #19) — `beginShutdown()` treated the IDE closing stdin as *"nothing upstream can deliver more than we can still print"* and immediately killed and reaped the ssh child. Every in-flight reply was discarded, and because the child's stdin went away with the teardown rather than closing on its own, the remote server never saw a clean EOF and never shut down. Both reported symptoms came from that one assumption.

  Shutdown is now a **half-close**: the bridge closes only its write side once the queue drains — `close()` on the ssh child's stdin pipe, `shutdown(fd, SHUT_WR)` on a tcp socket — and keeps reading until the remote closes its own end. This is what `ssh` itself does, which is why driving `ssh` directly always worked.

- **`--verbose` / `--silent` / `--debug` were inert in forward mode** (#18) — the `ulog` gates were assigned after `runForward()` had already returned, so forward mode produced no diagnostics and wrote no `--debug` log. Moved above the branch; both now work, which also makes forward mode debuggable at all.

- **`Bridge.deinit()` leaked `FwdState.write_q` / `carry`** on POSIX.

### Docs

- The `stdio+ssh://` hop reads your `~/.ssh/config` in full — the bridge runs the system `ssh` without `-F`. Documented, along with the three options it sets itself and therefore overrides (`-T`, `BatchMode=yes`, `ConnectTimeout=10`), and guidance for long-lived MCP sessions: `ServerAliveInterval` to turn a silently dropped connection into a clean exit 1, and `ControlMaster`/`ControlPersist` to cut respawn cost (measured ~0.87 s cold vs ~0.15 s multiplexed) for agents that terminate an idle stdio server.
- The remote account's login shell should be POSIX-compatible; the remote command string is POSIX-sh quoted.

### Verification

Linux (epoll) client → FreeBSD host, against a real stdio MCP server (`vnc-mcp-server` 0.9.1): full `initialize` + `tools/list` returns 22,889 bytes, byte-identical to the direct-`ssh` baseline. A long-lived session with stdin held open answers `initialize` at t+0.95 s, `tools/list` mid-session, a real `tools/call` after an idle gap, and exits 0 on stdin close.

New regression test `forward stdio+tcp: stdin EOF half-closes, late reply still delivered`, whose mock server withholds its reply until it observes the half-close — it fails against the pre-fix code. 84/84 tests pass; clean builds for `x86_64-freebsd`, `x86_64-linux-gnu`, `x86_64-windows-gnu`.

### Known issue

On **Linux**, a regular-file stdin or stdout hangs the bridge (`mcp-bridge ... > out.json`). `epoll(7)` rejects regular files with `EPERM` and the event port silently drops the failed registration, so the queue never drains. Not a regression — true of every release to date, not specific to forward mode, and not present on FreeBSD, where kqueue accepts regular files. It goes unnoticed because IDEs hand the bridge a pipe.

Tracked upstream as [pacyworld/born#4](https://pacyworld.dev/pacyworld/born/issues/4). A workaround was written and then deliberately reverted so the fix lands at the root instead.
